# 首次诊断指导价值：本地改动与验收记录

## 范围与状态

本轮仅增量修改首次诊断 Prompt、两个可选输出字段、现有诊断卡片和无追问分支，并补充本地测试。没有新增依赖，没有修改鉴权、录音或模型传输，没有提交、推送或部署，没有调用付费模型。

本报告的“优化后示例”来自人工编写的合成候选和 Mock 响应，不是真实模型输出。没有同输入、同模型的前后配对输出，不能宣称诊断准确率或自然度提升。

## 为什么这样改

原流程把具体组织线索主要留在补充后的 Guidance；首次诊断通常只有缺口和追问。用户可能知道需要补信息，却不知道从哪里回忆。

现在将三个用途分开：

| 用途 | 数据 | 展示位置与时机 |
| --- | --- | --- |
| 表达优化框架 | 复用 `expression_advice` | 首次诊断模块 02；针对原回答的前置、合并、压缩、衔接，不编补充结果 |
| 补充 / 回答思路 | 新增可选 `thinking_hints` | 首次追问下方只展示一组；进入补充页继续显示，Guidance 生成后隐藏 |
| Guidance 重说框架 | 原 `framework`、`keywords`、`reminder` | 用户提供实际补充之后生成；无追问时只组织已有信息 |

模块 02 改名「最值得优化的地方」，包含核心问题、影响解释、按需提供的表达优化框架与具体证据缺口。原来单独的表达建议卡片并入该模块，避免页面越改越长。模块 03 仍只出现一个核心追问，思路使用短语，并提示不必逐项回答。

## 契约变化

原必填字段、状态、输入 API、Guidance 与 Compare Schema 均保持不变。旧响应不提供新字段仍可校验和展示。

- `evidence_gap?: string | null`：最多 200 字，重要证据或事实澄清缺口的具体说明。无追问时只能省略或 null。
- `thinking_hints?: string[]`：省略、空数组或 2–4 条，每条最多 80 字，要求非空、唯一且不带问号或换行。无追问时只能省略或空数组。
- `expression_advice` 仍最多 3 条、每条最多 200 字；Prompt 建议每条尽量 60 字以内。结构路径必须提供非空建议，其他路径按实际价值选择；clear 不制造建议任务。

没有再增加一个同义的 followup_framework 字段。同一组 thinking_hints 是补充与追问的共享来源；前端对全半角、空格、标点差异进行保守去重，不做可能误删不同含义的模糊语义合并。原有单问题和逐字引文校验继续保留。

新字段不传入 Guidance 或 Compare，防止把“待回忆的线索”当成已经发生的事实。Guidance 只接收原回答、实际补充和已有 expression_advice；Compare 仍只比较原回答与最终自主重说。

## 修改前后示例

以下以合成文档助手案例展示规则与 UI 变化，不是新旧模型实测：

- 原回答已说“将 MVP 聚焦检索，没有先重做编辑器”，但没有解释依据。
- 修改前的机制：展示一个核心缺口与追问；表达建议是独立可选卡片，没有专门的回忆线索字段。
- 修改后的人工候选：表达优化框架为“保留范围选择与走查成果，把判断依据嵌入 MVP 取舍处”；证据缺口为“当时支持检索优先的具体需求或限制”；仍只追问“你当时优先做检索的主要依据是什么？”
- 回答思路为“当时最突出的用户需求 / 影响范围选择的实际限制 / 支持检索优先的判断依据”。这些是同一个问题的可选回忆角度，不宣称用户已经给出这些证据，不要求逐项回答。

## 待人工与真实模型验收

- 同一输入下模型能否判断“确实缺证据”和“只是结构问题”，而非总生成追问。
- 思路是否具体、口语化、足以帮助回忆；不同方向是否实为同一问题的可选线索。
- 输出是否紧扣已有信息、保留未完成项目的验证边界，且未生成未经确认的事实或完整范文。
- 真实模型是否稳定返回新字段及完整 JSON；本轮未修改 1800-token 上限或空 JSON 处理，不将工程测试视为该问题已解决。
- 移动端文字密度和可理解性仍需真实用户体验；浏览器视口检查不替代手机真机测试。

本轮不推送、不部署，所以线上不会自动出现这些改动。真实模型验收须另行确认费用。
